One day ≈ 295px wide — a title reads, and a lane is still 146px

At 375px a week gives each day 42px: a block is a single letter wide, an overlapping one 20px, and the drag target under the ~44px a finger needs. A block you cannot read is a block you cannot check.

The page owns the scroll. A 62vh grid knew nothing about the chrome above it or the dock below, so it hid 217px inside itself while the page still had 240px to go — and no fixed height fixes that, because the inbox below is variable. Cropping is what keeps one scroller honest: an uncropped 24h column would move the same excess into the page.

Correcting time from the grid

This is where a mistracked block is noticed, so it is where it gets fixed: a block opens the editor, dragging it adjusts its times, and clicking empty grid starts a new entry at the time clicked.

GestureResult
Click a blockOpens the editor
Drag a blockMoves it, preserving duration exactly
Drag an edgeResizes; past the other edge it clamps to 15 minutes
Click empty gridOpens the editor pre-filled, seeding one hour
"Add an entry on …"The same, reachable by keyboard
  • Drags snap to 15 minutes. A pointer lands on whatever minute a pixel happens to be, so an unsnapped drag bills 09:07–10:52 and calls it precision. The snap is what makes the gesture safe to offer on billable time at all.
  • A move preserves the duration; only a resize changes it. The end is derived by adding the original elapsed milliseconds, never by re-deriving a wall clock — a two-hour block dragged across a DST boundary is still two hours of billable work.
  • The gesture commits on release, past DRAG_THRESHOLD_PX. A block is also the control that opens the editor, so without a threshold every click lands a PATCH. The click that follows a drag is suppressed by a flag the click consumes — asking whether a drag is in progress cannot work, because pointer-up clears it before the click fires.
  • A billed or running block refuses the gesture and opens the editor, which says why. The billed lock is a database trigger, so a drag would 409 after the fact and spring back with no explanation.
  • Clicking empty grid opens the editor rather than writing a row. A click on a grid is too cheap a gesture to create a financial record from.
  • A drag is vertical, within one day. Moving an entry to another day is the rarer correction and the dialog already does it.
Time arithmetic
  • Never step days or weeks with + 86_400_000. Use startOfLocalDayOffset. A week containing a DST transition is 167 or 169 hours and a fall-back day is 25 hours long, so fixed-millisecond arithmetic lands an hour off and mis-buckets the entries at the edges.
  • Positions are fractions of the WINDOW, not the day. The column must be handed day.from/day.to rather than the day's own bounds, or every click lands at the wrong time. A click 50% down an 06:00→01:00 window seeds 14:30.
  • Each day carries its own exclusive end rather than reading the next column's start — which breaks the moment the list is one day, where the fallback would be the week's end, days away.
  • The DST tests assert a wall clock, not that minutes divide by 15. A fixed 24-hour denominator also lands on quarter hours — it just lands on the wrong ones.
One data path, two lenses

The fetch stays weekly regardless, so stepping within a week costs no request and rotating a phone needs no refetch — the day view is a lens over week data. The hook keeps one offset counted in days and derives the week from it; two offsets would drift apart the moment you crossed the breakpoint.

The arrows step whatever unit is on screen, so "back" always means "the previous one of these" — and the heading, total, empty state and legend all follow what is actually rendered.

This is useMediaQuery, not a Tailwind sm:, because a breakpoint that changes behaviour cannot be expressed in CSS. Reach for sm: first. Its server snapshot is false, so a component must render correctly as "wide" for one paint.
