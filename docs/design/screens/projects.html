The heading carries the client's rate, so an inherited row reads against it

Two surfaces, different jobs. /projects is where you find a project; the Projects region on a client is where you manage one in the context of its rate.

  • Each client is a region: its heading carries the client's swatch, and its projects are plain rows beneath.
  • Grouping is what makes a flat list readable. Three rows named "Website redesign" have to be decoded in one undifferentiated list; under client headings they do not.
  • "No client" is a heading, not an entity — it needs no detail page, no rate and no Edit button. It is also the only way to reach a project with no client, which the nested region structurally cannot.
  • It is never labelled "internal work". client_id = null covers three states the app cannot tell apart: genuinely internal, not yet assigned (billable work that will silently never be billed), and speculative. The inbox already treats the middle one as wrong, so an "Internal" heading would contradict it. isBillableDefault is the user's own answer.
  • An archived client keeps its own heading. Filing its projects under "No client" would be a lie, and they are exactly the rows someone checks when reviewing a finished engagement — which is why the list fetches clients with includeArchived.
  • The row shows the figure alone, not where it came from. Naming the source on each row restated the client heading immediately above it. ProjectRate resolves through resolveRate — the same function the invoice preview uses.
  • No resolvable rate renders in the danger channel, not as $0.00. Invoicing refuses to generate from unrated entries, so without it the failure is discovered at the moment of billing.

This is what makes two promises elsewhere true: that the numbers on an invoice are the numbers you worked (only honest if a mistake can be fixed), and that a runaway timer is surfaced rather than auto-trimmed (only honest if there is somewhere to do the trimming).

  • The inputs are local wall-clock; the API is UTC. toInstant resolves a date + time in a timezone by guessing UTC and correcting by the offset the guess lands in — DST-correct because the correction is computed at the target instant rather than assumed from today. Verified round-tripping across both US transitions, the ambiguous fall-back hour, a half-hour offset and UTC+14. Never do fixed-millisecond arithmetic here.
  • An end before the start is overnight. 22:00 to 02:00 is a four-hour shift; the end rolls forward one calendar day. Rejecting it is defensible and useless to someone who worked those hours.
  • An issued invoice locks the entry; a draft does not. guard_billed_entry returns early on a draft, because a draft holds no number and has not been sent. The dialog disabled on any invoiceId and so refused an edit the server would have accepted — the more expensive direction to be wrong in, since the fix for a wrong draft is to correct the entry and preview again.
  • The status is fetched, not embedded. It is not a column on the entry, so the dialog fetches the invoice — only when there is one, which is the rare case. test/shim.mjs passes the select string into raw SQL, so PostgREST's invoices(status) syntax would break every route test.
  • Deleting asks once. The row is one click from the duration and the delete is irreversible.
  • Creating supplies a UUIDv7, so a retried insert lands on the same row.
