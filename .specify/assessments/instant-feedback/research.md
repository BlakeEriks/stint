## Prior Art

- **PR #118** (closed, superseded by this assessment): built per-surface phase/pending state machines on web (`use-timer.ts`, `timer-bar.tsx`) and macOS (`TimerModel.toggle()`), blocked twice on unrelated PRs touching the same files, and was closed by Blake specifically because it missed the menu-bar "restart a recent task" path and left every other mutation unaddressed — closing comment: "closing this to be superceded by a feature dev instead with speckit." [source: `gh pr view 118 --comments`] (confidence: high)
- **Issue #11** predates #118's close and states the constraint the fix must respect: an optimistic start "must never claim green before the server confirms," and asks for every mutation/listing/transition to be walked at ~1s and ~3s of added latency. [source: gh issue #11] (confidence: high)
- Current web timer (`apps/web/src/lib/client/use-timer.ts:105-126`): `start`, `stop`, and `update` mutations have **no `onMutate`** — only `onSuccess`/`onError` calling `invalidate()` (a full refetch via `invalidateEntryData`). The bar shows stale state for the full round trip plus refetch, exactly as #11 describes. (confidence: high, cited)
- Current macOS timer (`apps/macos/Sources/Stint/TimerModel.swift:220-241`): `toggle()` is a plain `await`-then-`refresh()` sequence — `isBusy` is set true for the duration (disables re-entry) but nothing renders a predicted state; the UI only updates after the round trip. `stop` calls set `stats` early from the response (an exception, `TimerModel.swift:224-226`) but `start` does not touch `summary`/`isRunning` until `refresh()` returns. (confidence: high, cited)
- **Menu-bar "restart a recent task" path**: `TimerModel.resume(_:)` (`TimerModel.swift:243-262`). It guards `isBusy`, blocks with an explicit error message if a timer is already running (rather than queuing or silently no-op'ing — this is the principle-V-consistent behavior #118 apparently didn't cover for this specific call site), then awaits `api.startTimer` and `refresh()`. No optimistic/predicted UI update here either — same await-then-refresh shape as `toggle()`. This is the exact path issue-restated text says #118 missed.
- No shared mutation helper exists on web: 19+ `useMutation` call sites across `apps/web/src/components/*.tsx` and `apps/web/src/lib/client/*.ts`, each hand-writing its own `mutationFn`/`onSuccess`/`onError`; none use `onMutate`. [source: `grep -rn "onMutate\|mutationFn" apps/web/src`] (confidence: high) — searched explicitly for `createMutation`/`mutationHelper`/`useOptimistic`; none found.
- Other mutations checked for a "predicted result": `use-entry-drag.ts:57` (calendar drag) saves on drop with no visible optimistic branch beyond whatever local drag-state exists; invoice generation (`invoice-new.tsx:124`, `runPreview`/`generate`) has no obvious predicted result to show (a generated invoice number/PDF cannot be predicted client-side) — this is a real per-mutation gap the constitution note in intake.md already flagged.

## Data & Constraints

- Web `QueryClient` default `staleTime: 10_000` (`apps/web/src/components/providers.tsx:17`); `useTimer`'s own summary query overrides it to `staleTime: 0` and `refetchOnWindowFocus: 'always'` specifically because the default staleness window caused a stale bar on fast tab-back (comment at `use-timer.ts:67-71`). This means the *timer* row already has bespoke anti-staleness logic; other queries (clients, invoices, projects) still sit on the 10s default with no override. (confidence: high, cited)
- Route structure: no route under `apps/web/src/app/**` has a `loading.tsx` (`find … -iname loading.tsx` → empty). `(app)/clients`, `/invoices`, `/projects` are thin server wrapper pages (`export default function Page()`, not `async`) that just render a `<Suspense>` around a `'use client'` component (`ClientList`, `InvoiceList`, `ProjectList`) which does its own `useQuery` fetch; `(app)/calendar` doesn't even wrap in Suspense. So the route segment itself never awaits server data — the lag, if any, is client-side: fetch after mount, no skeleton/fallback content in the `<Suspense>` (no `fallback` prop passed), and no route-level prefetch since these pages carry `export const dynamic = 'force-dynamic'` (root `(app)/page.tsx`) or fetch client-side entirely.
- `next/link` usage in `nav.tsx:73` passes no explicit `prefetch` prop, so it takes Next's default; combined with no server-await and no `loading.tsx`, **the likely cause of tab-switch lag is client-fetch-after-navigate with no skeleton, not a missing Suspense boundary at the route level** — flagged as **INFERENCE**, not measured. No RUM/perf data exists to confirm; the intake's own unknown ("how much comes from missing loading boundaries vs. data fetching vs. render cost") is not resolved by static reading alone.
- `startedAt`: `StartTimer` schema marks it `startedAt: iso.optional()` (`packages/schema` L149) and the route defaults it server-side — `started_at: body.startedAt ?? new Date().toISOString()` (`apps/web/src/app/api/v1/timer/start/route.ts:34`). The schema *permits* a client-sent timestamp (comment nearby: "allows backdating a forgotten start"), but today's web `start` mutation (`use-timer.ts:105-107`) only sends `{ taskName, projectId }` — it never sends `startedAt`. macOS's `api.startTimer` call in `toggle()`/`resume()` also passes no timestamp. **In current practice, `startedAt` is server `now()`** even though the wire format would accept a client value. (confidence: high, cited — both schema and both call sites read directly)
- Constitution Principle I: one running timer enforced by the DB partial unique index (`one_running_timer_per_user`), and the API layer rule (`.claude/rules/api-layer.md`) reinforces "never pre-check the running timer before inserting... a pre-check is a race, the index is not." Any optimistic-start UI must tolerate a 409 `TIMER_ALREADY_RUNNING` rollback as the normal case, not an edge case — `use-timer.ts:109-113` already has that rollback comment ("Another device started one first. Reconcile rather than surfacing a failure").
- Principle V ("The App Never Silently Modifies User Data") and its `docs/design/principles.md` restatement both speak to *data correction*, not to *predicted-then-corrected UI state* — applying it to optimistic UI (must the rollback be visible, not just silent-revert?) is an extension the constitution doesn't yet make explicit. This is the open question intake.md already flagged; research did not find existing text resolving it.
- `docs/design/screens/timer-bar.html` ties green strictly to confirmed running state: `.clock.run { color: var(--accent-default) }`, `.transport.stop { background: var(--accent-default) }`, and prose at L291 warns two elements "would both be green often enough to confuse" if used loosely — i.e., the doc's existing model has exactly one thing wear the running-green at a time, which is in tension with a *predicted* (not-yet-confirmed) start also wearing it, per issue #11's explicit ask that "an optimistic start must never claim green before the server confirms."

## Evidence Against the Idea

- The single strongest piece of counter-evidence is #118 itself: a serious, tested attempt at exactly this problem (phase/pending state machines with rollback + two race-condition tests) was built and still missed a real path (menu-bar resume) and covered only the timer, not every mutation. That is direct evidence that "one shared mechanism" is harder to get complete than it looks, and a second attempt risks the same fate unless the menu-bar path and the full mutation inventory are treated as first-class acceptance criteria from the start (which the intake already does).
- There is no user demand signal beyond Blake's own use — this is pre-Alpha, single-operator. Spending constitution-level effort (a new principle plus an enforcement check) on responsiveness before there are outside users to feel the lag is a judgment call, not a validated need.
- The tab-switch-lag cause is inferred from code reading, not measured (no RUM, no profiling run in this research). It's plausible the real cost is render/query-cache-miss time rather than a missing `loading.tsx`, in which case adding loading boundaries would improve perceived-but-not-actual latency, or worse, mask a query that should be prefetched instead.
