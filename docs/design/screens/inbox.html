One row per entry

An unprojected entry gets its own row rather than joining a count, because the work is done one entry at a time: open it, assign a project, move to the next. A rollup names a number the user then has to go and find.

How a row is built
  • Each row is a card. bg-elevated, 8px radius, 10px/11px padding, a 6px gap, shadow-card, and no border on any edge. The dock's ground is the plane below it, so depth says where the card ends.
  • The title owns its line. It is the subject — every row is here because one identifiable thing wants a decision. A figure sharing that line takes width from it in proportion to how much money the row is about: measured at 286px, a real invoice title loses 42% to a five-figure amount. Truncating the subject to fit a fact means the card has to be hovered to be understood.
  • The figure drops to the meta line. It is a fact about the subject, not the subject, and beside the qualifier it reads as one statement — $2,340.00 · 20 days late — rather than two facts placed apart.
  • Severity is one 2px edge inside the card, and half the rows have none. danger is the overdue invoice, where money is already late; timer-warning is a length that wants a look. A stale draft and an unprojected entry are chores, so they draw nothing — two flagged cards among five is a signal, five is a texture.
  • The words carry the direction; color only ranks. The same amber means "too long" on one card and "too short" on the next, so the qualifier always names the threshold it tripped — over 8h, under 1m, 20 days late — and only that clause takes the color, never the client name beside it.
  • The title is always text-strong. A column of colored headlines reads as an outage.
  • Actions are text buttons with an icon, each carrying its own glyph. The check mark belongs to It's correct — the one action meaning "this is already right" — so no other action uses it.
  • The label is the verb; the accessible name carries the object. Mark paid reads cleanly in a row that already names its invoice twice, but a screen reader meets the buttons without that context — so every write and download sets an aria-label naming its invoice.
  • Two inline actions, or three on the timer row. The timer is the only row that needs a third, and the only one that sorts alone at the top.
The actions

Always drawn, and outlined — 1px solid at 5px radius. On a raised card a hover-only control has nothing to sit against, and the outline gives it its own edge instead of borrowing the card's.

  • Nothing fades in. A slot that reserves height for controls nobody can see costs the same space as drawing them, and a touch device has no hover to reveal them with. Drawing them is the shorter description and the one that works everywhere.
  • Hover moves the outline, not the layout. The border and the label brighten together on --motion-quick; no box changes size, so a pointer crossing the dock never reflows it.
  • Only Discard takes color, on its own hover, in both its border and its label. It is the one action here that destroys something.
A row leaving

An answered row fades, then the gap closes behind it. This is the one place in the app that animates a box's size, and the gap closing is why: a row that vanishes leaving a hole reads as a rendering fault, and the rows below arriving instantly gives no account of where the answered one went.

  • The refetch waits for the exit. The row stays in the query data until its animation has finished, so nothing has to be reconstructed once it goes. Refreshing first drops the row instantly and leaves the exit playing over a gap.
  • The gap collapses by grid-template-rows: 1fr → 0fr on a wrapper, which interpolates without measuring a height. Nothing pins a pixel value and nothing reads the rows below. The row's own vertical padding goes to zero on the same curve — a 0fr track still floors at its content's min-content height, so without that the gap stops closing short.
  • A card's 6px margin goes with it. Padding alone was enough when rows were flush bands; a card carries its own gap, and a collapsed track with a live margin leaves 6px of empty dock behind every departing row. margin-block runs on the same curve as the padding and the track.
  • --motion-quick with --ease-accelerate — an object leaving speeds up as it goes. The fade is --motion-instant, so the text is gone before the box closes; the other order reads as the row being crushed.
  • Every kind leaves the same way. An inline write (Mark paid, Mark sent, It's correct), a save or a delete in the entry editor, and the runaway's Keep all play the one exit — one way for a row to go, not five. The editor holds its refetch until the row has finished, so an entry given a project collapses rather than blinking out from under the closing dialog.
  • The runaway row rides a synthetic id, because it comes from the timer and has no record of its own. Keep is local state and still plays the exit.
  • prefers-reduced-motion removes the animation, and the row goes at once.
What each row may do
  • The rows write, narrowly. Marking an invoice paid or sent is offered inline, because that is the action that legitimately clears a row — the underlying fact changed.
  • The runaway row surfaces; it does not correct. Keep touches nothing and dismisses the notice — stopping the timer would be the app editing billable work. Adjust stops first, then opens the editor. Discard asks once. dismissed resets when the overrun ends, so Keep silences that overrun rather than the feature.
  • An unprojected row opens the entry dialog in place. These entries scatter across days, so the column below — which is today alone — would not reach them.
  • Rows are derived per request. A stale row claiming money is late after it arrived is the same trust failure as silently editing hours.

The two flags

A long timer stays long and an entry of unusual length keeps that length forever, so those two rows cannot clear the ordinary way. Each carries a flag instead — dismissed on the running timer, duration_ok on the entry. Both record an answer the user gave about one object and die with it, which is what separates them from a snooze.

Strange duration

A stopped entry whose length is implausible. Thresholds live on user_settings as min_entry_seconds (60) and max_entry_hours (8). Both are nullable and default to null, so the row is opt-in: null switches off that side, and null on both retires the row. duration_ok is a column on the entry.

A minute is the short threshold, not an hour. An entry under a minute was started and stopped without work between, where a twenty-minute call is ordinary billable work the app must never question.

  • It is about a record, not a timer. A running timer past the long threshold is a runaway and shows that row — never both.
  • A billed entry never fires it. An issued invoice locks the entry, so the row would offer an edit that cannot happen.
  • An unprojected entry is one row, not two. Both facts can hold of the same record, but it is one entry and one decision, and two rows about it read as the inbox repeating itself. Unprojected wins: it blocks invoicing outright, where an implausible length still bills.
  • One row per entry, short or long. Each row is a decision about one record, and a row naming a count is a row the user has to go and act on somewhere else.
  • "It's correct" sets duration_ok on that entry. Editing the entry to a plausible length clears the row the ordinary way, by making the condition false.
  • Changing an entry's times clears duration_ok, in a trigger rather than in the route, so the answer cannot outlive the length it was given about. An entry confirmed at 9h and later edited to 14h is a new question.
Ordering and presence

The runaway timer sorts first — the one row about time being recorded wrongly right now, where an overdue invoice is equally late in an hour, and the only row whose subject changes while you read it. Overdue invoices sort next and carry danger; the rest carry warning. Never the accent.

An invoice fires at due date + 7 days, because paying on day 32 of net 30 is ordinary and a row that flags it trains the user to clear the list without reading it. The invoice page still shows the true due date; this governs only when the inbox speaks up.

It is always present, including when it is empty

An inbox is a place, which is why it is named for one rather than for a predicate. Every row is shown — the grace periods keep the list short enough that the count is the summary.

At zero the count slot is empty and “Nothing needs you.” carries the state alone. The count is a count.

Today, beneath it

The dock holds the inbox, then today drawn as a day column — the same 44px hour /calendar uses, so a block is the same object at the same scale in both places. The inbox answers what needs you; the column answers where the day went, which is the question that catches an hour nobody tracked.

The head answers what the day was worth; the foot totals what it took. A region's figure sits beside its title everywhere else on the screen, and money is the day's conclusion. The hours are how it was reached, so they go under the column that adds up to them — where a sum needs no label to be read as one.

The accent appears once. The now-line and the running block it terminates are one subject — the live thing — and the running block is the only one that carries the accent fill.

The foot does not scroll. It sits outside the column's own scroller, because a sum that scrolls away is a sum you have to go looking for. It appears only on a day with entries — a total of nothing is the empty state's job.

Money is absent rather than zero while it loads. A $0.00 that resolves to a real figure a moment later reports a day that earned nothing and then takes it back. A day that genuinely earned nothing — unrated work, or a timer still running — renders $0.00, which is the answer.

The column is read-only

A block opens the entry dialog, which is where a correction is typed. Empty grid does nothing: at this width the gap between two blocks is a few pixels of ambiguity, and the timer bar owns starting work. /calendar keeps the drag, so the dock is the same column with the gestures off.

A running block is not a button. Its end does not exist yet and the dialog refuses it; the timer bar owns retitling mid-run. It is still drawn — a column missing it has a hole at the one place the eye goes — and it counts up to the now-line and stops there.

Dividing the column

The dock spans the full height at xl and does not scroll. Each region scrolls inside its own share, so neither pushes the other off: an inbox that scrolls away is an inbox you forget, and a calendar crushed to a sliver is one you cannot read.

The hairline between them is the handle that sets the ratio — dragged, or nudged with the arrow keys once focused, and Home recenters it. It carries the rule’s own weight at rest and shows a grip under the pointer.

Below xl

The dock is a band beneath the content, sized by what it holds. There is no height to divide, so there is no handle — and the grid sits at its full window with the page carrying the scroll.

Never
  • Nothing destructive beyond the timer. Voiding and deleting an invoice belong on the invoice itself, where the whole document is in view — a stray click on a glance must not destroy a financial record.
  • The inbox cannot be hidden. Structural rather than a rule to enforce: it is not a card, so there is nothing to switch off. A region that surfaces problems is worthless if it can be turned off, and the user most likely to turn it off is the one it exists for. The split handle resizes it and stops at a quarter for the same reason.
  • No snooze. Hiding a row whose condition is still true and unanswered makes the inbox something dismissed reflexively rather than read.
  • No inbox row is green, including the runaway row, whose subject is the running timer. test/ui/inbox.test.tsx asserts it. In the column below, the accent belongs to the now-line and the block it terminates — the live thing, which a row about a problem is not.
  • The dock itself is never a card. It is painted on the ground and carries no surface of its own — the rows are the objects, and the column holding them is not one. A container around them would put a card inside a card.
