One row per entry

An unprojected entry gets its own row rather than joining a count, because the work is done one entry at a time: open it, assign a project, move to the next. A rollup names a number the user then has to go and find.

How a row is built
  • Two lines, then the action slot. A title, a figure and three buttons do not share one line at any dock width worth having.
  • Severity is a 2px left rule — danger for an overdue invoice, timer-warning for everything else. Colour alone never carries the meaning: the qualifier line states it in words.
  • The title is always text-strong. A column of coloured headlines reads as an outage.
  • Actions are text buttons with an icon, each carrying its own glyph. The check mark belongs to It's correct — the one action meaning "this is already right" — so no other action uses it.
  • The label is the verb; the accessible name carries the object. Mark paid reads cleanly in a row that already names its invoice twice, but a screen reader meets the buttons without that context — so every write and download sets an aria-label naming its invoice.
  • Two inline actions, or three on the timer row. The timer is the only row that needs a third, and the only one that sorts alone at the top.
Revealing the actions

Actions appear on :hover and :focus-within, so a resting row is content rather than a control panel. On a touch device they are always visible — there is no hover to reveal them.

  • The action slot is always in flow; only its contents fade. display:none removes the slot, so the row grows the moment a pointer crosses it. The slot reserves its height and the buttons animate opacity alone.
  • The reveal is --motion-instant with --ease-standard, flat across the group — this is a surface crossed fifty times a day.
  • Only Discard takes colour, on its own hover. It is the one action here that destroys something.
A row leaving

An answered row fades, then the gap closes behind it. This is the one place in the app that animates a box's size, and the gap closing is why: a row that vanishes leaving a hole reads as a rendering fault, and the rows below arriving instantly gives no account of where the answered one went.

  • The refetch waits for the exit. The row stays in the query data until its animation has finished, so nothing has to be reconstructed once it goes. Refreshing first drops the row instantly and leaves the exit playing over a gap.
  • The gap collapses by grid-template-rows: 1fr → 0fr on a wrapper, which interpolates without measuring a height. Nothing pins a pixel value and nothing reads the rows below. The row's own vertical padding goes to zero on the same curve — a 0fr track still floors at its content's min-content height, so without that the gap stops closing short.
  • --motion-quick with --ease-accelerate — an object leaving speeds up as it goes. The fade is --motion-instant, so the text is gone before the box closes; the other order reads as the row being crushed.
  • The runaway row leaves the same way, on a synthetic id, because it comes from the timer and has no record of its own. Keep is local state and still plays the exit — one way for a row to go, not two.
  • prefers-reduced-motion removes the animation, and the row goes at once.
What each row may do
  • The rows write, narrowly. Marking an invoice paid or sent is offered inline, because that is the action that legitimately clears a row — the underlying fact changed.
  • The runaway row surfaces; it does not correct. Keep touches nothing and dismisses the notice — stopping the timer would be the app editing billable work. Adjust stops first, then opens the editor. Discard asks once. dismissed resets when the overrun ends, so Keep silences that overrun rather than the feature.
  • An unprojected row opens the entry dialog in place. These entries scatter across days, so the today-only list would not reach them.
  • Rows are derived per request. A stale row claiming money is late after it arrived is the same trust failure as silently editing hours.

The two flags

A long timer stays long and an entry of unusual length keeps that length forever, so those two rows cannot clear the ordinary way. Each carries a flag instead — dismissed on the running timer, duration_ok on the entry. Both record an answer the user gave about one object and die with it, which is what separates them from a snooze.

Strange duration

A stopped entry whose length is implausible. Thresholds live on user_settings as min_entry_seconds (60) and max_entry_hours (8). Both are nullable and default to null, so the row is opt-in: null switches off that side, and null on both retires the row. duration_ok is a column on the entry.

A minute is the short threshold, not an hour. An entry under a minute was started and stopped without work between, where a twenty-minute call is ordinary billable work the app must never question.

  • It is about a record, not a timer. A running timer past the long threshold is a runaway and shows that row — never both.
  • A billed entry never fires it. An issued invoice locks the entry, so the row would offer an edit that cannot happen.
  • An unprojected entry is one row, not two. Both facts can hold of the same record, but it is one entry and one decision, and two rows about it read as the inbox repeating itself. Unprojected wins: it blocks invoicing outright, where an implausible length still bills.
  • One row per entry, short or long. Each row is a decision about one record, and a row naming a count is a row the user has to go and act on somewhere else.
  • "It's correct" sets duration_ok on that entry. Editing the entry to a plausible length clears the row the ordinary way, by making the condition false.
  • Changing an entry's times clears duration_ok, in a trigger rather than in the route, so the answer cannot outlive the length it was given about. An entry confirmed at 9h and later edited to 14h is a new question.
Ordering and presence

The runaway timer sorts first — the one row about time being recorded wrongly right now, where an overdue invoice is equally late in an hour, and the only row whose subject changes while you read it. Overdue invoices sort next and carry danger; the rest carry warning. Never the accent.

An invoice fires at due date + 7 days, because paying on day 32 of net 30 is ordinary and a row that flags it trains the user to clear the list without reading it. The invoice page still shows the true due date; this governs only when the inbox speaks up.

It is always present, including when it is empty

An inbox is a place, which is why it is named for one rather than for a predicate. Every row is shown — the grace periods keep the list short enough that the count is the summary.

Never
  • Nothing destructive beyond the timer. Voiding and deleting an invoice belong on the invoice itself, where the whole document is in view — a stray click on a glance must not destroy a financial record.
  • The inbox cannot be hidden. Structural rather than a rule to enforce: it is not a card, so there is nothing to switch off. A region that surfaces problems is worthless if it can be turned off, and the user most likely to turn it off is the one it exists for.
  • No snooze. Hiding a row whose condition is still true and unanswered makes the inbox something dismissed reflexively rather than read.
  • Nothing here is green, including the runaway row, whose subject is the running timer. test/ui/inbox.test.tsx asserts it.
  • No card on the dock. An elevated row competes with the real cards in the column beside it.
